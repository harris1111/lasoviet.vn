# LSV79 click receipt verification

The reminder's opaque delivery ID travels in a canonical checkout fragment, which the invisible client removes before POSTing a strict receipt. Admission requires a verified owner, current offers consent/preferences, exact delivery fingerprint, live owned chart/version and the pending unexpired immutable order/continuation/intent. FreeAI and Recovery coordination locks precede SHARE/SKIP LOCKED commerce reads. A concurrent payment cannot establish a retrospective click. Replay keeps the initial clock and captured/sent classification. An order and a delivery each have at most one receipt. Official purge removes receipts before recovery delivery payloads.

The default mode is disabled; only the existing capture mode is supported. No SMTP/worker activation, payment confirmation, order creation or wallet mutation is introduced. The current payment schema cannot durably prove production-provider provenance, so there is no monetary projector: the database CHECK requires `attributed_at`, `paid_vnd` and `charged_la` all null. Bare UTM and nearby payment timestamps remain insufficient. The runbook separates capture/sent/eligible-click counts and records the remaining provenance requirement without claiming recovered revenue.
